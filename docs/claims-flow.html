Claims platform · presentation notes

Claim lifecycle, step by step

One motor claim followed from login to payment. Each step shows what happens while the user waits (synchronous REST), what happens afterwards through Kafka, and exactly which database tables change.

What this project is

An insurance claims management platform for an APAC insurer that handles motor and property claims across six markets (Singapore, Hong Kong, Australia, Malaysia, Thailand, Indonesia). It is a full-stack web application: Java Spring Boot microservices behind an API gateway, Kafka for events, PostgreSQL with one database per service, and one Angular application split into micro-frontends.

The problem today

Claimants report by phone or email and get no visibility afterwards. Claims staff work from shared inboxes and spreadsheets with no view of their workload. Managers have no real-time picture of outstanding claims or how much money the company owes on them.

What the platform changes

Claimants report and track claims online. Every claim follows one controlled lifecycle with an audit trail. Staff get a prioritised work queue. Managers see workload and liability exposure live.

Deliberately out of scope

Document and photo uploads, real payment execution, email and SMS (logged stub only), live currency rates, self-registration of claimants. Each is a planned next step, not a gap in the design.

Two building blocks used in every write step

Outbox: the "to-send" tray

claims-service never calls Kafka inside a user request. In the same database transaction as the claim change, it inserts a row into outbox_event. A background job (every 1 second) reads unsent rows, publishes them to Kafka, and sets published_at.

Why: either both the claim change and the event are saved, or neither. Kafka being down never loses an event and never fails the user's request.

processed_event: "already handled" list

Kafka can deliver the same message twice (for example after a crash). Each consumer inserts the eventId into its own processed_event table in the same transaction as its business change. If the id is already there, it skips.

Why: a duplicate never creates two notifications or adds a payment to the policy twice.

While the user waits

  1. Browser sends POST /api/auth/login with email and password to the gateway. This is the only public route.
  2. Gateway forwards to identity-service, which finds the user and checks the password against the BCrypt hash.
  3. identity-service returns a JWT containing user id, name, role CLAIMANT and market SG, valid for 60 minutes.
  4. The Angular shell stores the token, reads the role and loads the claimant micro-frontend.

No Kafka: nothing else in the system cares that someone logged in. From now on every request carries Authorization: Bearer <JWT>; the gateway and each service verify it.

Claimant submits the claim (FNOL)

Alice · claims-service → policy-service, then Kafka
SYNCKAFKA

While the user waits

  1. POST /api/claims with policy number, type MOTOR, incident date, location, description, estimated loss SGD 8,000.
  2. claims-service validates the input. Bad input → 400 with field errors.
  3. Sync call to policy-service: GET /internal/policies/SG-MOTOR-1001/coverage. Checks: policy active, belongs to Alice, incident date inside the policy period, product matches. Returns sum insured, deductible, currency.
  4. Not covered → 422 "Incident date is outside the policy period". Policy-service down → circuit breaker → 503. In both cases nothing is saved.
  5. Covered → claims-service works out priority (Strategy rules), SLA due date and initial reserve min(8000, sumInsured) − deductible.
  6. One database transaction writes three rows, then commits.
  7. Returns 201 with claim number CLM-SG-2026-000124, status SUBMITTED. Alice sees a confirmation.
READpolicypolicy_db (via REST)
INSERTclaimstatus SUBMITTED, coverage snapshot, reserve
INSERTclaim_status_history— → SUBMITTED
INSERToutbox_eventClaimSubmitted, published_at = null

After the response

  1. Outbox relay picks up the row within about 1 second and publishes ClaimSubmitted to claims.lifecycle.v1 (key = claim id).
  2. On Kafka acknowledgement, it marks the outbox row as sent.
  3. notification-service consumes it, checks it has not seen this event id, creates "We received your claim CLM-SG-2026-000124" for Alice.
  4. policy-service also receives it (same topic, its own consumer group) and ignores it, because it only reacts to ClaimSettled.
UPDATEoutbox_eventpublished_at = now
INSERTnotificationnotification_db, for Alice
INSERTprocessed_eventnotification_db
Why the coverage check is synchronous: Alice must know right now whether the claim is accepted; a claim on an expired policy should never be created. Why the coverage is copied onto the claim: later screens and dashboards never need to call policy-service again, so the two services stay loosely coupled.

What happens when something breaks

policy-service is down during step 3

Circuit breaker opens after repeated failures. Claimant gets 503 "Please try again shortly". No claim row is created, so there are no half-checked claims.

Kafka is down

Users notice nothing: claims are saved and the response is normal. Events wait in outbox_event with published_at empty. The relay sends them once Kafka is back.

notification-service is down

Events stay in Kafka. When it restarts, it continues from its last committed offset. Notifications arrive late, none are lost.

Same event delivered twice

The second insert into processed_event hits the primary key, so the consumer skips it. No duplicate notification, no double payment on the policy.

Two officers pick up the same claim

The version column lets only the first update succeed. The second officer gets 409 and a refreshed queue.

A malformed event

The consumer retries 3 times with back-off, then moves it to claims.lifecycle.v1.DLT so it does not block the events behind it.

Five lines to say out loud

  1. If the user needs an answer now, it is REST; if other services need to know something happened, it is Kafka.
  2. The only synchronous service-to-service call is the coverage check, and its result is copied onto the claim so it never has to be repeated.
  3. claims-service writes the change and the event in one transaction through the outbox, so the two can never disagree.
  4. Events are keyed by claim id for per-claim ordering, and every consumer is idempotent, so redelivery is harmless.
  5. Each service owns its database; the only things crossing boundaries are REST contracts and the event schema.
